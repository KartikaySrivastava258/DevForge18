flow:
  - A webhook or a schedule starts an execution; the first nodes normalise and validate the input and answer 400 with a specific reason when it is wrong.
  - The workflow checks whether this request has already been handled — a lookup backed by a unique constraint, or an idempotency key in Redis — and answers clearly (for example 409) if so.
  - For a risky action, it answers the requester at once (202), pauses at a Wait node and sends the resume link to approvers only; a timeout branch handles no answer.
  - After approval, it calls external APIs within the Redis rate limit, with capped, delayed retries, routing failures through error outputs to a deliberate answer.
  - It records the outcome and the decision in PostgreSQL; if the execution still fails, the error workflow alerts someone.
  - Separately, CI runs the Postman collections with Newman, so a changed or broken API is caught before a workflow fails in production.

## When to use it

Use this shape for the many small processes between existing systems in an office or a team: registrations,
reminders, form handling, routing support requests. Each one is plain glue between services, where a platform saves
building and maintaining connectors, and where the people who own the process should be able to read the workflow.

It is the wrong home for logic that is core to a product and needs full testing and control — write a service — and
for scheduled data pipelines that need backfills and reviewed code, which belong in the Batch data platform with
quality gates. If data must not leave your own infrastructure, that is a reason to self-host n8n as here rather than
use a hosted automation service.

## How it works

Every workflow follows the same four steps: validate, deduplicate, act, record — with an error path. Validation
happens before anything is written; deduplication relies on a unique constraint in PostgreSQL or an idempotency key
in Redis rather than on a lookup alone; actions that cost money or cannot be undone wait for a person; and every
outcome, including each decision and who made it, is recorded. One shared shape also makes the workflows easier to
read and hand over to the people who will own them.

The instance itself is treated as a sensitive server, because it holds credentials for every system it touches:
credentials are encrypted with a key kept outside the workflows, data lives in a backed-up database, risky nodes are
blocked, and it runs behind TLS and authentication. Postman collections in CI watch the boundary with the outside
world, so an external API that changes breaks a build rather than a live workflow.
