## Brief

A college's registration office keeps students, courses and enrolments in spreadsheets. Every term someone is
enrolled twice, enrolled in a cancelled course, or recorded with an email that belongs to another student — and
nobody can say quickly how many seats are left. You will move the data into PostgreSQL and make **the database
itself** enforce the rules, so that bad data cannot get in no matter which program or person writes it.

The starter fixes the table and column names (other programs depend on them) but has no rules at all: any
row is accepted. The README lists eight rules and one report. Turn each rule into a constraint, write the
report as a view, and add sample data that shows it working.

This is the core skill of relational design: deciding what must always be true about the data, and declaring it
where it cannot be bypassed.

## Getting started

1. Copy the starter files into a new folder. You need PostgreSQL 16 — either installed locally, or the Docker
   container from "Tables, rows and constraints".
2. Load the starter into a scratch database and see that it accepts nonsense:

   ```bash
   createdb registration
   psql -v ON_ERROR_STOP=1 -d registration -f schema.sql -f seed.sql
   psql -d registration -c "INSERT INTO courses VALUES ('X', NULL, 99, -5)"   # accepted — that is the problem
   ```

3. Edit `schema.sql` rule by rule. To start again from empty: `dropdb registration && createdb registration`.
4. Write `seed.sql` with invented students (use addresses at `college.example`, a domain reserved for examples).
5. Run the check from the folder above your project. It needs Docker: it starts its own throwaway PostgreSQL,
   loads your files into fresh databases and removes the container afterwards.

   ```bash
   bash check.sh path/to/your/project
   ```

   For each rule the check inserts data that should be refused, and reports `PASS` only if PostgreSQL refuses it
   *because of a constraint* — a typo that makes the statement fail for another reason does not count.
