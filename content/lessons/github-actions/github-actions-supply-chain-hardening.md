## The idea in one sentence

Every `uses:` line runs someone else's code with your workflow's permissions, so pin each action to an **exact commit SHA**, let **Dependabot** keep the pins current, and publish **provenance** so others can verify what you built and where.

## Explain it like I'm twelve

Your class uses a recipe from a famous cookbook, "chapter 7". If someone swaps the pages of chapter 7, the next class cooks the wrong thing — the chapter *name* stayed the same. Writing down the exact page's fingerprint instead (a SHA) means a swapped page is noticed at once. A librarian checks for new editions and suggests updates (Dependabot), and the school stamps every dish "cooked in our kitchen, from recipe X" (provenance).

Where the analogy breaks: the "fingerprint" is a cryptographic hash, so swapping the page without changing it is practically impossible.

## What problem it solves

Attackers increasingly target build systems: compromise one popular action, and every workflow that trusts its tag runs the attacker's code with access to secrets and tokens. Pinning removes the "trust the tag" step; updates stay safe because they arrive as reviewed pull requests; and provenance lets your users check that a binary or image really came from your pipeline.

## How it works

![](media:github-actions/supply-chain.svg)

- A tag (`@v7`, even `@v7.0.1`) is a movable name, resolved when the workflow runs. A full 40-character **commit SHA** names exactly one commit. Keep the version as a comment: `uses: actions/checkout@<sha> # v7.0.1`.
- **Dependabot** (`.github/dependabot.yml`, ecosystem `github-actions`) opens pull requests that bump the SHA and the comment together.
- **Workflow dependency lockfiles** (`.github/workflows/actions.lock`, generated by the `gh actions-lock` extension) go further: they also pin the actions your actions use. GitHub calls them the strongest protection available.
- **Artifact attestations** (`actions/attest`, with `id-token: write` and `attestations: write`) sign a statement of which workflow, repository and commit produced a file or image; `gh attestation verify` checks it.

## Try it yourself

> **Local lab** — needs Git and internet access (to read tags from github.com), as in the earlier lessons. Every command is run automatically in DevForge's tests.

### 1. A tag can move

```bash run
mkdir -p pinning-lab && cd pinning-lab
git init -q upstream-action && cd upstream-action
echo 'echo "deploying safely"' > deploy.sh && git add . && git commit -q -m "Safe deploy" && git tag v2
reviewed=$(git rev-parse HEAD)
echo 'echo "deploying safely"; echo "sending secrets elsewhere"' > deploy.sh && git commit -q -am "Malicious change"
git tag -f v2 > /dev/null   # the tag is moved to the new commit
cd ..
echo "v2 now points to:   $(git ls-remote "$PWD/upstream-action" refs/tags/v2 | cut -c1-7)"
echo "the reviewed commit: ${reviewed:0:7}"
git -C upstream-action show "$(git ls-remote "$PWD/upstream-action" refs/tags/v2 | cut -f1):deploy.sh"
git -C upstream-action show "$reviewed:deploy.sh"
```

```text output
v2 now points to:   …
the reviewed commit: …
echo "deploying safely"; echo "sending secrets elsewhere"
echo "deploying safely"
```

Anyone using `@v2` now runs the second line too. Anyone who pinned the reviewed commit's SHA still runs exactly what was reviewed.

### 2. Pin real actions to SHAs

```bash run
mkdir -p .github/workflows
cat > .github/workflows/test.yml <<'EOF'
name: Test

on: [pull_request]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7.0.1
      - uses: actions/setup-node@v7.1.0
        with:
          node-version: 22
      - run: npm test
EOF
cat > pin.sh <<'EOF'
#!/usr/bin/env bash
# Rewrites "uses: owner/repo@tag" to "uses: owner/repo@<commit SHA> # tag" in a workflow file.
set -euo pipefail
file="$1"
grep -oE 'uses: [A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+@v[0-9][0-9.]*' "$file" | sort -u | while read -r _ ref; do
  repo="${ref%@*}"; tag="${ref#*@}"
  # An annotated tag lists its commit as "<tag>^{}"; a lightweight tag points at the commit directly.
  sha=$(git ls-remote "https://github.com/$repo" "refs/tags/$tag" "refs/tags/$tag^{}" | sort -k2 | tail -n 1 | cut -f1)
  [ ${#sha} -eq 40 ] || { echo "could not resolve $ref"; exit 1; }
  sed -i "s|uses: $repo@$tag\$|uses: $repo@$sha # $tag|" "$file"
done
EOF
chmod +x pin.sh && ./pin.sh .github/workflows/test.yml
grep 'uses:' .github/workflows/test.yml
```

```text output
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
```

These SHAs are the commits the `v7.0.1` and `v7.1.0` tags pointed to when this lesson was checked. If a tag is ever moved, this workflow keeps running the reviewed commits.

### 3. Updates as reviewed pull requests

```bash run
cat > .github/dependabot.yml <<'EOF'
version: 2
updates:
  - package-ecosystem: "github-actions"
    directory: "/"            # checks the workflows in .github/workflows
    schedule:
      interval: "weekly"
    groups:
      actions:
        patterns: ["*"]       # one pull request for all action updates
EOF
grep -E 'package-ecosystem|interval' .github/dependabot.yml | sed 's/^ *//'
```

```text output
- package-ecosystem: "github-actions"
interval: "weekly"
```

Dependabot proposes new SHAs (and updates the `# v…` comments) in pull requests that your CI tests and a person reviews — pinned *and* current. Repositories that adopt workflow dependency lockfiles (`gh actions-lock`) get the same for transitive dependencies too.

### 4. Provenance for what you release

```bash run
cat > .github/workflows/release.yml <<'EOF'
name: Release

on:
  push:
    tags: ["v*.*.*"]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write          # to sign the attestation
      attestations: write      # to store it
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Build the release archive
        run: tar -czf course-site.tar.gz README.md
      - name: Attest build provenance
        uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
        with:
          subject-path: course-site.tar.gz
EOF
echo "release.yml uses: $(grep -oE 'uses: [^ ]+' .github/workflows/release.yml | cut -d@ -f1 | cut -d' ' -f2 | tr '\n' ' ')"
```

```text output
release.yml uses: actions/checkout actions/attest
```

After a release, anyone can run `gh attestation verify course-site.tar.gz -R OWNER/REPO` to confirm the archive was built by this workflow, in this repository, from the tagged commit.

## Common mistakes

- **Pinning to short SHAs or to `@main`.** Only a full 40-character SHA is immutable.
- **Pinning without updating.** Old pins miss security fixes; use Dependabot (or lockfiles) and review the pull requests.
- **Broad default permissions.** Set `permissions: contents: read` at the top and grant more per job.
- **`pull_request_target` with a checkout of the pull request's code.** It runs untrusted code with write tokens and secrets; avoid it, or never execute the checked-out code.
- **Treating provenance as a quality check.** It proves where something came from, not that it is safe.

## Where this fits in a real system

The same discipline applies across the supply chain: pinned base images and SBOMs in the **Docker** track, lock files for npm or pip, `terraform providers lock` in **Terraform**, and **Kubernetes** admission policies that only admit images whose provenance verifies. **Jenkins** plugins and shared libraries deserve the same pinning.
