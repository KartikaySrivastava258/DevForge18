## Facts confirmed (source → wording)

- Container registry (docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry): images at `ghcr.io/NAMESPACE/IMAGE_NAME`; in a workflow, `GITHUB_TOKEN` can publish packages associated with the workflow repository (needs `packages: write`).
- Reusable workflows (…/actions/how-tos/reuse-automations/reuse-workflows): `on: workflow_call`; inputs and secrets defined there; files must be directly in `.github/workflows` (no subdirectories); `secrets: inherit` passes all secrets; reusable workflows can be nested.
- Composite actions (…/actions/tutorials/create-actions/create-a-composite-action): `runs: using: "composite"`; every `run` step needs `shell`; inputs read via `${{ inputs.x }}` passed through `env`; `$GITHUB_ACTION_PATH`.
- Environments (…/actions/reference/workflows-and-actions/deployments-and-environments): required reviewers (up to six users or teams; reviewers need read access), wait timer (1–43,200 minutes), deployment branches and tags; environment secrets and variables. On Free, Pro and Team plans, required reviewers and wait timers are only available for public repositories.
- OIDC (…/actions/concepts/security/openid-connect, …/reference/security/oidc): workflows exchange short-lived tokens with the cloud; the cloud checks the token's subject and other claims against the role's trust conditions. Subject for an environment: `repo:ORG/REPO:environment:NAME`; for pull requests `…:pull_request` only if the job uses no environment. `aud` defaults to the repository owner's URL; issuer `https://token.actions.githubusercontent.com`.
- OIDC in AWS (…/security-harden-deployments/oidc-in-aws): the job needs `permissions: id-token: write`, which only allows requesting the token, not writing resources; AWS IAM recommends evaluating `token.actions.githubusercontent.com:sub` in the trust policy.
- Secure use (…/actions/reference/security/secure-use): pin actions to a full-length commit SHA (a bad actor would need a SHA-1 collision); workflow dependency lockfiles are "the strongest protection available, and supersede SHA pinning for repositories that adopt it".
- Workflow dependency lockfiles (…/actions/concepts/security/workflow-dependency-lockfiles): `.github/workflows/actions.lock`, generated by the `gh actions-lock` CLI extension, never edited by hand; pins every action including transitive ones, not reusable workflow calls (pin those by SHA); the locked commit must be reachable from the recorded branch or tag; supports Dependabot updates.
- Dependabot for actions (…/code-security/dependabot/…/keeping-your-actions-up-to-date-with-dependabot): `.github/dependabot.yml`, `package-ecosystem: "github-actions"`, `directory: "/"`, `schedule.interval`.
- Artifact attestations (…/use-artifact-attestations): permissions `id-token: write`, `contents: read`, `attestations: write`; verify with `gh attestation verify PATH -R ORG/REPO` (and `oci://` image references).
- Secrets (…/use-secrets): secrets cannot be referenced directly in `if:` conditionals.
